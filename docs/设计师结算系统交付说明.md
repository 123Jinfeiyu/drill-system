# 设计师结算系统 · 交付说明（本地版）

> 依据：《数字结算系统操作指南》课件画面（七大模块）独立设计实现
> 定位：在 `E:\drill-system` 本地跑一套**双角色**设计师结算系统，与既有 OPC 一人公司系统同底座
> 设计规格见同目录 `设计师结算系统设计规格.md`

---

## 一、一句话说明

**派单员在总后台录设计师、登订单、盯流程、给钱；设计师用手机号在结算端看单、点「一键结算」、查收益。**
两边各自独立登录，规则全部由同一份规则层裁定 —— 页面上写的每一条限制，后端都真的会拦。

## 四、课件规则 → 代码落点

所有规则**只在** `backend/app/services/settle_ledger.py` 里实现一次，路由只调用不重复。

| 课件要求 | 规则层函数 | 效果 |
| --- | --- | --- |
| 佣金比例 50%，最高 70% | `validate_commission_rate` / `calc_commission` | 越界直接拒绝并给出原因，**不产出金额** |
| 战区 / HR 必须留空 | `validate_designer` | 非空 → 422 + 按字段列问题 |
| 订单编号初稿后补 | `check_transition`（到 `finalizing`） | 没编号进不了终稿阶段 |
| 两类截图缺一不可 | `check_transition`（到 `pending_audit`） | 缺聊天记录截图 / 缺交付文件截图，分别提示 |
| 接单 60 天内有效 | `check_settle_eligibility` | 过期单进不了结算 |
| 每月 8-9 号窗口 | `settle_window` | 非窗口期发起 → 409 + 下次开放日期 |
| 结算必须设计师主动触发 | 派单员端**没有**发起接口 | 派单员只能「标记已打款」 |
| 每月 7 号前提醒 | `remind_designers` | 看板直接给可打电话的名单 |
| 六类常见异常 | `diagnose_order` | 订单详情页顶部直接列出问题 + 处理方案 |
| 删除按状态区分 | `check_deletable` | 制作中可删；已交付提示联系客服 |

## 五、订单状态机

```
设计待定 pending_design
   │ 派单（必须指定在职设计师）
   ▼
初稿制作中 drafting
   │ 节点一：必须填订单编号
   ▼
终稿制作中 finalizing
   │ 节点二：必须上传两类截图
   ▼
待审核 pending_audit
   │ 审核通过（检查 60 天有效期）
   ▼
可结算 settleable
   │ 设计师在 8/9 号窗口点「一键结算」
   ▼
结算中 settling
   │ 派单员标记已打款 + 流水号
   ▼
已结算 settled

支线：审核驳回 rejected → 回到终稿制作中
      已取消 canceled（仅「设计待定」前可取消）
```

跳阶段一律不允许。

## 六、与总系统的互通（两系统真正打通的地方）

### 6.1 三层结构

```
backend/app/services/trcipg_client.py   上游适配器（令牌缓存 / 0.4s 限流 / 401 重登）
backend/app/services/opc_sync.py         OPC 撮合侧的字段映射 + 差异对账
backend/app/services/settle_bridge.py    ★ 结算侧的桥接：上游记录 → 本地台账
backend/app/routers/settle.py            3 个桥接端点（status / preview / import）
frontend/src/pages/SettleBridgePage.tsx  「总系统互通」页（派单员端）
```

### 6.2 互通原则：**只读、单向、不回写**

上游是生产系统，本地结算系统是它的**下游视图**。

- 上游 → 本地：可以（拉数据）
- 本地 → 上游：**不做**。任何写回上游的动作都没有实现，也不打算实现。

### 6.3 三个端点

| 端点 | 干什么 |
| --- | --- |
| `GET /api/settle/admin/bridge/status` | 上游配没配、连不连得上、通行模式 |
| `GET /api/settle/admin/bridge/preview?kind=designers\|orders` | 导入前预览，逐条标「可导 / 有问题」+ 问题原因 |
| `POST /api/settle/admin/bridge/import` | 执行导入。**幂等**，按上游 ID 去重 |

界面入口：派单员端导航「结算系统 → 总系统互通」（`/settle/bridge`）。

### 6.4 翻译规则（不是复制，是映射）

| 上游 | 本地 | 备注 |
| --- | --- | --- |
| `teamMembers.id` | `upstream_id` | **幂等键** —— 上游手机号不唯一（1437 人里 3 个重复） |
| `phone` | `phone` | 登录账号，本地唯一 |
| `war_zone` / `hr_name` | **不导** | 课件要求这两栏留空，上游有值也不带过来 |
| `allow_settlement=0` | 备注留痕 + 标为有问题 | 禁结算的人不该被派单 |
| `status=0` | `disabled` | 上游已停用 |
| `order.status`（1~9） | 本地状态机 | 见 6.5 |
| `order_commission` | `order_amount` | 项目总金额 |
| **佣金比例** | `commission_rate` | **反推**：`designer_commission ÷ order_amount` |

### 6.5 上游状态 → 本地状态（双向）

| 上游 status | 上游含义 | 本地状态 |
| --- | --- | --- |
| 1 | 初稿制作中 | `drafting` |
| 2 | 终稿制作中 | `finalizing` |
| 3 | 已交付 | `pending_audit` |
| 4 | 验收中 | `pending_audit` |
| 5 | 验收成功 | `settleable` |
| 6 / 7 / 8 | 问题处理相关 | `finalizing`（本地是「终稿返工中」） |
| 9 | 已完结 | `settled` |

未知状态一律落 `pending_audit` —— 宁可停住等人看一眼，也不要猜成「已完结」把账结错。

### 6.6 佣金比例是**反推**的，越界要标出来

上游只给金额不给比例。本地规则硬区间是 50%~70%，反推值越界说明这笔单是**旧规则下**产生的。

处理方式：**导入，但标出问题**，不硬拒 —— 硬拒会让台账跟上游对不上；
也不能悄悄放进去 —— 结算时比例对不上会扯皮。所以预览表和导入结果里都会明确列出。

反推不出来（金额为 0 或佣金为 0）时返回 `None`（**比例未知**），不是 0。
拿 0 去填会被规则层当成「比例 0，越界」，把一笔数据不全的单说成违规单，冤枉人。

### 6.7 本地演示数据源

上游不是随时能连的。为了让互通链路随时能完整跑一遍（演示、教学、回归测试），
加了一个环境变量：

```bash
SETTLE_FAKE_UPSTREAM=1 .venv\Scripts\python.exe -m uvicorn app.main:app ...
```

启用后走 `settle_bridge.FakeUpstreamClient`，数据照真实上游的字段形状造，
**刻意带了各种问题**（9 位手机号、停用、禁结算、比例越界、查无此人的设计师），
这样预览页上的「可否导入 / 问题」两列才有东西可看。

**不设这个环境变量时，一切照常走真实上游。**

### 6.8 佣金口径已用真实数据验证

用**上游 300 条真实订单**验证过恒等式：
`designer + hr + qc + control == order_commission`（100% 成立）；
`design_supervisor_bonus` 是额外支出，**不参与**分账和。

## 八、两个必须知道的坑

### 8.1 结算窗口每月只有 8、9 号 —— 其余时间跑不通完整链路

这是课件的硬规则，不是 bug。为了本地能演示 / 自动化能实测，加了一个环境变量：

```bash
SETTLE_FAKE_TODAY=2026-11-08 .venv\Scripts\python.exe -m uvicorn app.main:app ...
```

它把「今天」钉死到指定日期，所有窗口判断随之生效。**不设就用真实日期**（生产别设）。

### 8.2 金额一律 Decimal，禁浮点

结算金额差一分钱就是账务事故。全链路 `Numeric` + `Decimal`，
`ROUND_HALF_UP` 量化到分。前端只做展示格式化，**不改值**。
