# 设计师结算系统 · 设计规格（本地版）

> 依据：用户提供的《数字结算系统操作指南》课件画面（七大模块）
> 目标：**在本地跑一套可用的设计师结算系统**，并与既有两个内部系统互通
> 技术底座：`E:\drill-system`（沿用已有 FastAPI + React + AntD 栈）

## 一、课件要点 → 系统规则对照表

课件画面里的每一条操作要求，都必须落成**可执行的代码规则**，而不是只写在页面上。

| 课件要求 | 出处 | 落地规则 |
| --- | --- | --- |
| 派单员在总后台录入设计师信息 | 模块二 | `POST /api/settle/designers`，必填项按课件列表逐项校验 |
| 「所属战区」「所属HR」必须留空 | 模块二·核心注意 | 录入接口**主动拒绝**非空值，返回明确提示 |
| 登录密码由派单员设置，建议临时密码 | 模块二·关键提醒 | 录入时生成临时密码并标记 `must_change_password`，设计师首次登录强制改密 |
| 设计师账号录入后才能登录结算端 | 课件·关键前置条件 | 设计师端登录只认已录入且启用的账号；未录入 → 明确报错「尚未开通」 |
| 客户 ID 必须与平台名称完全一致 | 模块三·客户ID | 订单登记校验客户 ID 非空；**不做模糊匹配**，错了就是错了 |
| 设计师佣金比例 50%，最高 70% | 模块三·佣金结构 | `commission_rate` 硬校验 `[0.50, 0.70]`，越界直接拒绝并给出原因 |
| 订单编号在初稿完成后补录 | 模块三·订单编号 | 订单登记时编号可空；进入「待交付」前**必须**有编号，否则门禁拦住 |
| 所属战区按订单归属选择 | 模块三·基础信息 | 订单必填 `war_zone`，从战区字典选 |
| 对接客服填真实姓名 | 模块三·基础信息 | 订单必填 `customer_service` |
| 订单类型区分个人接单/内部协作/外部合作 | 模块三·任务与类型 | `order_type` 枚举，三选一，影响结算归属 |
| 初稿完成后更新订单编号 | 模块四·节点一 | 状态流转到 `drafting` 时强制带编号 |
| 终稿完成后上传「终稿通过」聊天截图 | 模块四·节点二 | 流转到 `delivered` 前**必须**有 `chat_screenshot` |
| 终稿完成后上传交付文件截图 | 模块四·节点二 | 流转到 `delivered` 前**必须**有 `file_screenshot` |
| 两类截图齐全才算流程闭环 | 模块四·底部提示 | 交付门禁：两类截图缺一不可 |
| 接单时间需在两个月内 | 模块六·结算条件 | 超过 60 天的订单**不能进入结算**，明确提示失效原因 |
| 每月 8 日-9 日开放结算 | 模块六·结算条件 | 结算窗口：仅 8/9 两天可发起，其余日期按钮禁用并提示开放日 |
| 设计师主动点「一键结算」才发起 | 模块六·结算条件 | 结算必须由设计师端触发，**系统不自动发起** |
| 每月 15 号为统一打款日 | 课件·结算与打款时效 | 打款日常量与倒计时展示 |
| 派单员每月 7 日前提醒设计师 | 模块六·派单员职责 | 看板显示「待提醒设计师」清单 + 距 7 号的提醒 |
| 六大常见异常 | 模块五 | 异常诊断器逐条识别并给处理方案 |
| 退款/删除按订单状态区分 | 模块五·退款删除规则 | 制作中 → 可直接删；已交付 → 禁止删，提示联系客服 |

## 二、系统边界（不做什么）

1. **不碰真实系统的写接口** —— 真实总后台的 add/edit/settle 一律不调用。
2. **不做资金通道** —— 只记录「已打款 + 流水号 + 截图」，实际转账走支付宝手工。
3. **不做权限体系** —— 只有两个角色：派单员、设计师。
4. **不做多租户** —— 一套库，一家公司。

## 四、状态机

```
pending_design  设计待定（可派单）
      │ 派单
      ▼
drafting        初稿制作中（要求：已填订单编号 draft_no）
      │ 提交终稿
      ▼
pending_audit   待审核（要求：两类截图齐全）
      │ 审核通过
      ▼
settleable      可结算（要求：接单时间 ≤ 60 天）
      │ 设计师点「一键结算」（仅 8/9 号）
      ▼
settling        结算中
      │ 打款（每月 15 号）
      ▼
settled         已结算
```

分支：`rejected`（审核驳回）→ 回到 `drafting`；`canceled`（取消）仅在 `drafting` 前可删除。

## 五、结算条件（模块六，硬规则）

| 条件 | 规则 | 不满足时的提示 |
| --- | --- | --- |
| 接单时间 ≤ 60 天 | `order_date + 60天 >= 今天` | 「订单接单已超过两个月，无法进入结算」 |
| 结算窗口 = 每月 8、9 日 | `today.day in (8, 9)` | 「结算入口仅每月 8 日-9 日开放，当前 {date} 未开放」 |
| 主动触发 | 只有设计师端「一键结算」按钮能发起 | 派单员端**没有**发起结算的按钮 |
| 打款日 = 每月 15 号 | 展示倒计时 | — |

## 六、六大常见异常（模块五）

| # | 异常 | 识别条件 | 处理方案 |
| --- | --- | --- | --- |
| 1 | 订单金额不符 | 订单金额 ≠ 客户确认金额 | 核对原始需求单，差额需客户确认后修正 |
| 2 | 订单号不存在 | 订单编号格式非法或查无对应 | 找客服拿真实编号后补录 |
| 3 | 缺少订单编号 | `order_no` 为空 | 初稿完成后在详情页补录 |
| 4 | 商务口径单 | `order_type=internal` 且无归属战区 | 内部协作单必须指定战区才能结算 |
| 5 | 设计师佣金不符 | 比例越界或金额对不上 | 按 50%-70% 重新核算，超 70% 需变动协议 |
| 6 | 未确认稿件 | 缺两类截图之一 | 让设计师补交终稿通过聊天记录与交付文件截图 |

## 七、两套界面

### 派单员端（总后台对应）

1. **业务看板** —— 漏斗（待派单/制作中/待审核/可结算/已结算）、本月业绩、待提醒设计师、结算窗口倒计时
2. **设计师管理** —— 录入表单（按课件字段）、临时密码生成、启停
3. **订单登记** —— 完整表单，佣金比例实时校验
4. **订单流程** —— 列表 + 详情抽屉，两个节点的专属操作区
5. **结算管理** —— 可结算清单、结算单列表、标记打款
6. **异常处理** —— 异常诊断器
7. **总系统互通** —— 预览上游数据 → 导入本地（只读、单向、幂等）

### 设计师端（结算端对应）

1. **我的订单** —— 名下订单进度
2. **一键结算** —— 仅 8/9 号可用，列出可结算订单
3. **收益明细** —— 结算历史

### 互通页为什么是「先预览再导入」两步

一键直接导的话，派单员看到的是一堆没头绪的表格，
不会知道哪条能导、哪条不能、为什么不能。
预览页逐条给出「可导 / 有问题」和问题原因，导入后还会再给一份跳过明细 ——
**每条没导进去的记录都要说清楚为什么**，否则数据对不上时会互相怀疑。

## 八、与真实系统互通

本地系统是**独立可用**的，同时保留一条**只读、单向**的通道，把总系统的数据搬进来：

| 端点 | 干什么 |
| --- | --- |
| `GET /api/settle/admin/bridge/status` | 上游配没配、连不连得上、通行模式 |
| `GET /api/settle/admin/bridge/preview?kind=designers\|orders` | 导入前预览，逐条标「可导 / 有问题」+ 原因 |
| `POST /api/settle/admin/bridge/import` | 执行导入。**幂等**，按上游 ID 去重 |

另有 OPC 撮合侧的一套只读端点（`/api/opc/upstream/*`），用于撮合业务的同步与对账。

**只读、单向、不回写**。理由：真实系统是生产系统，回写权限一旦扩散，出了错没人查得清。
本地结算单确认无误后，由派单员**手工**在真实后台核对。

### 8.1 三层分工

```
trcipg_client.py   上游适配器 —— 令牌缓存 / 0.4s 限流 / 401 重登
settle_bridge.py    ★ 翻译层 —— 上游记录 → 本地台账（纯映射，不碰网络）
settle.py           路由层 —— 调上游 + 落库 + 说清结果
```

翻译层是纯函数，好测。所有映射规则集中在 `settle_bridge.py`，
路由层不重复实现任何映射逻辑。

### 8.2 幂等键用上游 ID，不用手机号

上游 1437 个设计师里有 **3 个手机号重复**（同一人多条档案）。
拿手机号做键会撞唯一约束、抛 `MultipleResultsFound`。
所以 `sl_designers.upstream_id` 与 `sl_orders.upstream_id` 存上游 ID，作为幂等键。

### 8.3 战区与 HR 不导

课件明确要求这两栏留空。上游有值也不带过来 ——
别把上游的组织架构污染进本地台账。

### 8.4 佣金比例是反推的

上游只给金额不给比例。`commission_rate = designer_commission ÷ order_amount`。
反推不出来（金额 0 或佣金 0）时是**比例未知**（`None`），不是 0。
越界不硬拒 —— 硬拒会让台账跟上游对不上；但会明确标出问题，结算前人工核对。

### 8.5 状态映射保守优先

未知上游状态一律落 `pending_audit` ——
宁可停住等人看一眼，也不要猜成「已完结」把账结错。
